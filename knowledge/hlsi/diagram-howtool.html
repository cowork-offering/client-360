Data flow · sequence

How a tool call resolves

One banker question becomes one tool call. The fleet composes the answer in code, and the regulated number is computed before the model ever sees it. Read top to bottom.
1
The banker asks Reasoning client · Claude / Agentforce
A single tool call goes to the Customer 360 MCP: tools/call customer360_show_ews { accountId }. The model orchestrates; it does not fetch or compute.
2
Read, as the banker Customer 360 MCP · nCino + FSC
The server authenticates run-as-user (OAuth, WITH USER_MODE) and reads the relationship, exposures and covenant thresholds. Native Salesforce sharing and FLS decide what this banker may see.
3
Fan out, in parallel Aggregation tier, acting as an MCP client
It calls the system MCPs at the same time over streamable-HTTP (tools/call, 8s timeout, graceful-null so one slow source never blocks the view):
Boom
spread & ratios
boom_get_ratios
AFS
servicing behaviour
revolver_utilization
Snowflake
risk migration
iris_get_signal
4
Join and compute, in code Aggregation tier · Product Package + Account spine
Results are joined on the one spine and the regulated number is formed here: ratio × threshold → pass / watch / breach. The number is born in code, not in the model.
SR 11-7 wall
above: code computes  ·  below: model only narrates
5
Return a small result Back to the reasoning client
Only the computed grades and KPIs travel back, not the raw spread. The payload is small and already final.
6
Rank and narrate Reasoning client
The model ranks the fired signals and explains them in plain language. It never recomputes the number it was handed.
7
Commit, gated later phase
If a human commits a decision, a write goes back to nCino and an audit record to the Snowflake ledger. Reads are v1; writes come later, behind the gate.
Verified in experience-mcp/src/boomFinancials.js — the aggregation MCP is itself a client to the system MCPs (JSON-RPC tools/call over streamable-HTTP).
