**The 7 tools, plain terms:**

| Tool | What it reads |
|---|---|
| `Customer360Snapshot` | Thin anchor — account basics + Package-level exposure rollups (TCE/TBE/TOE), never sums Loan amounts directly (limit/sublimit structure double-counts) |
| `Customer360RelationshipGraph` | Ownership graph (`LLC_BI__Connection__c`, the populated one — 208 edges org-wide) + deal-party roles (`LLC_BI__Legal_Entities__c`: Borrower/Guarantor/Co-Borrower). | `Customer360Exposure` | Facilities + collateral (modern `LLC_BI__Loan_Collateral2__c`, NOT the legacy empty one) + a computed coverage-shortfall flag. Owns the collateral query so nothing else duplicates it |
| `Customer360Covenants` | Modern `LLC_BI__Covenant2__c` only (legacy `LLC_BI__Covenant__c` = 0 records org-wide, a real trap) — threshold, actual, status, next test date |
| `Customer360Opportunities` | Standard Opportunity — whitespace/NBA candidates |
| `Customer360StructuralSignals` | Deliberately narrow: modification clustering, renewal/maturity proximity, guarantor distress ONLY. Covenant/financial/behavioral/risk-migration EWS already live elsewhere in the fleet (`deal_covenant_grade`, Boom, AFS, Snowflake) — not duplicated here |
| `Customer360SearchAccounts` | Find an account by name/industry to get the ID the other 6 need |

Read-only by design (v1 scope, matches this project's own earlier decision — see
`VALIDATION-AND-DECISIONS.md`). Write tools can be added later the same way (new class, new

## 2. The trust incident — what happened and why the final build is actually solid

Early this session I (a) wrote a full Apex class with **invented** nCino field/object names, no
schema check, and (b) separately claimed "no Salesforce access" without checking that a live
`sobject-sf` MCP connector was already connected in the session. Both were wrong; got corrected
hard by Fabian, root-caused, logged to `feedback.md` as a standing rule ("verify before asserting
Salesforce schema or tool access"). Mid-fix, also destroyed `feedback.md` with a careless test
command — caught it via `wc -l`, recovered cleanly from the offsite GitHub backup + local git repo
in `~/brain/memory/`, verified the restore matched `HEAD` exactly, zero data loss.

**Net effect: the SECOND build (what's live now) is fully schema-verified**, not the same as the
first wrong one. Every object/field in `sf-build-v2/` was checked live via
`sf sobject describe --use-tooling-api` before use, not assumed. The original wrong `sf-build/`
folder has been deleted from the knowledge base (was already removed from the deployed project
earlier). If you ever see a reference to it, it's stale — ignore it.

**Also corrected mid-build:** the entire Apex "shape" was wrong on the first pass too — a single
dispatcher class implementing an invented `ConnectApi.McpToolResult` API. Real Salesforce Hosted
MCP servers don't work that way — confirmed against Salesforce's own Apr/May 2026 docs+blog (GA
Apr 29 2026) and a real working example already in the org (Noland's `CreditMemoExperinece`
server). Real shape: one plain Apex class per tool, one `global @InvocableMethod` each, standard
`List<Request>→List<Response>`, auto-published to Salesforce's API Catalog, referenced from
`McpServerDefinition` via `<tools><apiDefinition><apiIdentifier>aa:apex-{ClassName}</apiIdentifier>
<apiSource>API_CATALOG</apiSource><operation>{ClassName}</operation></apiDefinition></tools>` — and
`<tools>` is a REPEATED top-level element (one block per tool), not one block with many
`apiDefinition` children (that fails deploy). A `<toolName>` element inside each `<tools>` block is
also required — its absence fails deploy with an unhelpful server-side NPE, not a clear schema
error. All of this is documented in the header comments of the actual deployed files — read those
before touching the XML again.

Also ran an architecture review with Clawdy before finalizing the 7-tool split — caught two real
overlaps (household/KYC both hitting the same Connection graph; exposure/EWS both wanting
collateral) and merged/scoped them cleanly. That's why it's 7 tools, not 8 or 9.

## 3. Architecture Q&A — settled, don't re-derive

A long back-and-forth after the build landed on these conclusions. Treat all of these as decided,
not open:

- **UI capability:** Salesforce Hosted MCP servers (the `McpServerDefinition` mechanism used here)
  are **tools/data only** — verified two ways: live Tooling API schema for both
  `McpServerDefinition` and `McpServerToolDefinition` (no resourceUri/mimeType/UI field anywhere),
  and the real deploy errors along the way. Independently confirmed via a Clawdy consult (see
  below) — verdict held.
- **Identity model:** Salesforce Hosted MCP is **per-user OAuth+PKCE only** — no documented
  server-to-server "on behalf of" / token-exchange mechanism. This means **experience-mcp can never
  fetch Customer360 data server-side** the way it fetches Boom (`boomFinancials.js`-style). The
  agent (Claude) must connect to Customer360 directly, itself, as the actual authenticated user,
  and pass the fetched data INTO the widget tool as an argument — same "agent-passed wins, no
  server fallback" shape already proven for the `financials` arg on `deal_show_summary`, just
  without the fallback leg (experience-mcp structurally can't do that fallback for Customer360).
  **This is the single most load-bearing constraint for the widget build — don't try to make
  experience-mcp fetch Customer360 itself.**
- **Where the UI actually gets built:** `experience-mcp/widget/customer-360.html` (new file,
  doesn't exist yet — only `deal-summary.html` and `finalize.html` exist there today) + a new tool
  in `experience-mcp/src/... ` wired via `experience-mcp/app/api/[transport]/route.js` (the file
  that registers `deal_show_summary` today — read it, it's the exact pattern to copy). Build step:
  `node scripts/build-widget.mjs`. Real gotcha already hard-won and documented in that file's
  comments: the widget receives ONLY `content[0].text` — `structuredContent` and `_meta` are both
  stripped by the host, a `_meta`-only payload silently renders "No deal data."
  - Verified there is no widget-agnostic hosting need for Customer360 itself — it runs entirely on
    Salesforce's own infra (like `CreditMemoExperinece`), zero servers of ours to stand up for it.
- **Plugin structure:** build a NEW sibling plugin `customer-360-reinvented`, NOT folded into
  `credit-memo-reinvented` (that one's scoped to the deal-level 10-step underwriting workflow, 14
  skills already, different domain). Matches the existing convention (`boom-mcp`/`afs-mcp`/
  `experience-mcp` are already separate sibling repos).
- **Plugin `mcpServers` auto-bundling (parked, not started):** a Claude Code plugin's
  `.claude-plugin/plugin.json` CAN declare an `mcpServers` key so installing the plugin
  auto-connects its MCP server(s) — confirmed real/documented. Our own `credit-memo-reinvented`
  plugin does NOT currently use this (its connectors are wired some other way, not traced). Fabian
  wants to try this properly on `customer-360-reinvented` — **Fabian and Noland personally, on this
  engagement, not "Connectry" as a brand** — before Noland adapts the pattern back into
  `credit-memo-reinvented`.
- **MCP "Prompts"** (`McpServerPromptDefinition`, sibling to the Tool type used here) — real,
  verified schema, confirmed **zero rows anywhere in the org** (nobody's used this yet, including
  Noland). Wraps a Salesforce Prompt Template as a user-invocable one-click starter. Possible future
  fit, not explored beyond confirming it exists.
- **Salesforce Multi-Framework (React-hosted apps via UIBundle)** — confirmed separate/parallel to
  MCP, no dependency either way. Own prior verified runbook: `salesforce-multiframework-verified.md`
  (a "Hello Memo" React app already proven live in this same `bankinggpt` org). One real future
  convergence point: Salesforce's own roadmap lists **"MCP UI" as a planned future Multi-Framework
  framework option** alongside React — if shipped, a widget could run natively in Salesforce AND
  render in Claude from one build. Roadmap only, not live.
- **AXL / "HXL" (Agentforce Experience Layer)** — real, TDX 2026, part of "Headless 360." Genuinely
  can render UI natively across Slack/Claude/ChatGPT/Agentforce from one definition — but it's a
  **separate runtime from `McpServerDefinition`**, not an extension of it, and it's in **beta/
  Developer Preview** — confirmed not provisioned in this org (checked live: zero `EntityDefinition`
  hits for Headless/Experience-Layer/HXL/AXL). Independently verified via a Clawdy consult (Fabian
  explicitly asked for a second opinion, not a rubber stamp) — verdict: my finding holds, AXL is the
  right track to watch for real Salesforce-native UI-in-MCP-hosts later, not something that changes
  today's build. Official name per Clawdy's sourced link: **Agentforce Experience Layer (AXL)** —
  "HXL" is how the public playground itself is branded, slightly inconsistent naming in the wild,
  same real product.
- **Write capability:** confirmed explicitly NOT present in any of the 7 tools (all read-only SOQL,
  no DML). Matches the project's own prior "v1 = read-only" decision. Extensible later, same
  mechanism, but should follow the fleet's existing gated (`EXPERIENCE_ALLOW_WRITES`-style switch)
  + audited (`log_audit_event`) write pattern, not ship bare.
- **Schema sophistication vs. data population — two different questions, don't conflate them.** The
  underlying nCino/FSC schema is genuinely sophisticated (35-role Connection taxonomy, real HMDA
  compliance fields, proper lien-position stack modeling, covenant grace-period tracking, a 3-layer
  org/approval model). What's uneven is SEEDED DATA for any one demo account — Piedmont is rich on
  credit/exposure/covenants/collateral, thin on deposits/treasury/profitability/KYC-on-file/peer
  data. That's why a second demo account (**Timothy Norton Household**, real deposit balance
  $910,800, real FSC household grouping) exists — it covers what Piedmont can't.
